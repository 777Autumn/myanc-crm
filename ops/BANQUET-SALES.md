# 婚宴 CRM 销售到交接实施记录

## 当前使用与收尾

销售录入、原生提醒、Word 材料、指定接手和退回新版的主体流程已在虚构环境上线。
下文为最初实施过程的历史快照，其中“未上线”等时态不代表当前状态；实际版本与
验收以 `ops/releases/` 的对应发布记录为准。本次审查收尾的代码、GitHub、Mac 状态
分别记录，不能用公式创建成功或本地测试代替真实旅程。

### 原生工作台配置

使用 [展示公式模板](banquet-display-fields.example.json)，按顺序创建四列；部署前
将表达式中的交接表名替换为实际表名，关联列必须引用婚宴真实 record ID。
四列只用于显示，不加入 `banquet.fields` / `handoff_fields`、审批事实或 schema 哈希。
原有业务字段来自 `myanc_crm/banquet.py` 的 `SCHEMA` / `HANDOFF_SCHEMA`，不得改写
既有字段 ID。单选选项：销售阶段为新线索、跟进中、已约到店、已到店、已签单、
已流失；日期为待确认、预计、已确认；跟进为待跟进、已完成、已取消；交接为
待接手、已接手、已退回。客户、婚宴、跟进、交接保留各自关联记录。

- `handoff-pending`：婚宴表的新 grid 视图，销售阶段为已签单、展示交接状态不等于
  已接手；包括未提交、待接手、已退回和异常，每场婚宴一行。
- `handoff-mine`：交接表的新 grid 视图，指定接手人匹配宿主映射的 CRM 用户 ID、
  确认状态为待接手、展示版本判定为当前；每位成员独立配置视图 ID。
- 原来的我的待跟进、到店安排、销售阶段视图保持不变。先核对公式正常、异常、
  同名、改名、换人和新版重算，再将代码及上述两个入口配置同次切换；保留旧视图。
- 原生提醒仍由婚宴跟进时间触发，条件为跟进状态待跟进，收件人为记录当前销售
  负责人，内容为业务名称、下一步及记录链接；批准者不替代负责人。同一计划不得
  另建 ANC 个人提醒。改期、换人、取消分别核验实际通知，不能只看工作流已启用。

视图筛选不授予权限。当前 test 的编辑范围仅为虚构共享 Base，不启用高级权限，
不授予私人 Base 权限，不扩大个人 CLI scopes；Bot 写入仍须本人预览审批。
人工修改相关业务字段后，旧审批必须重新预览。版本和关联异常只显示为异常，
不得用计算列替代宿主对发布记录、指定接手人、连接和文件的检查。

### 维护与回退

复用 [发布合同](RELEASE.md) 和 [维护入口](MAINTENANCE_START.md)。历史故障记录
保留原状态；新候选的维护调用方只接受绑定候选、完整记录/审批哈希和原始故障证据的
两条精确例外。安装前重新检查原执行进程已退出、相关锁可取得、没有对应业务写入，
任一未知变化停止维护。不修改通用终态白名单，不重放旧维护回执。

回退保留新增写前连接守卫；不能保留时停用交接写入。账本、凭据、历史失效记录不回滚。
成员授权断开或换绑后，旧任务不能恢复；重新连接后按既有新会话流程另起。

## 初始实施历史（非当前状态）

授权范围：当前测试团队，777秋、test、共同群，虚构资料。飞书保存正式业务
事实；ANC 复用个人读取、宿主固定身份、预览审批和读回。旧客户、历史记录、
模拟项目均保留。首期不包含财务、合同签署、库存、锁档或全流程执行。

基线：CRM `99aae72bbc746e520afb2663f07924dd68021334`，Gateway
`8df349e9edba693e0529ceb08e8c26dc78351c2f`。本次使用独立工作树，未改线上。

必须交付：

- 客户与宴会分表；固定字段查询、建档、修改、关联真实跟进；明确未知事实。
- 原生“我的待跟进、到店安排、销售阶段、待交接、我的待接手”视图。
- 原生提醒验证人工/Bot 写入、改期、换负责人、取消；失败则保留未完成，
  不搭新调度系统、不产生双份通知，批准者不等于当前销售负责人。
- 签单材料默认 Word，绑定具体版本；提交者确认后待接手；指定接手人在
  自己会话确认或退回；改材料/接手人形成新版。文件送达与接手分别记录。
- 错误身份、旧卡片、重复点击、不可读文件、失效连接及中途失败均有对照。
- 分别记录逻辑、真实模型、真实飞书结果；核对表、工具、最终文件和回执。
- 精确提交独立 Spec/Standards、PR CI、合并 CI、三仓固定候选、Mac 维护，
  唯一接收器与至少 125 秒稳定窗口。完成前分别报告三层未完成项。

本地实现：销售查询/审批/读回、指定交接/退回/新版、材料快照验权及工具接线
已实现。Linux Python 544 项（4 项平台条件跳过）、Gateway core/actionhost
相关测试与显式 CUJ 通过。跨仓销售 CUJ 使用真实 Engine、HTTP、子进程和
SQLite，仅替换模型、飞书传输及外部 Base；不能计作真实模型验收。

测试团队：婚宴及交接表、跟进关联字段、五类原生视图已建立；虚构建档经真实
API 和候选代码审批逻辑写入，两个个人连接读回一致。原生提醒仍在验证：首轮
脚本的修改返回 record_not_found，不能计作改期/取消/换负责人通过。
真实 Bot 销售及签单交接、完整原生提醒旅程、独立审查、GitHub 交付和 Mac
发布均未完成；新增工具未启用到线上。最终证据随发布记录另行固定。

首轮独立审查发现私聊婚宴预览缺少个人连接绑定、长跟进预览截断及卡片翻译
未复用统一入口。已修补并加入原版本失败的回归：私聊预览使用本人读取，执行
复核冻结连接版本；跟进超过 2000 字符拒绝；卡片统一使用 Gateway i18n。
修补后的 Linux Python 549 项通过（4 项条件跳过），Gateway 全量回归与精确
提交复审仍在进行。原生提醒第二轮已观察 test 收到正常和换负责人提醒、改期
后收到改期提醒，未出现取消提醒；人工填表及 Bot 写入的完整对照仍未完成。

部署时仅将已核验的 `banquet` 配置合并到原有受保护 CRM 配置：固定婚宴表、
交接表及字段映射、原跟进表的关联婚宴字段，以及 `banquet_workbench` 映射。
个人视图通过宿主核验的 CRM 用户 ID 选择；群内不得凭个人视图取得权限。不要把测试资源 ID
写入通用模板。缺少完整映射时新增能力拒绝；旧客户能力继续沿用原配置。

员工使用：先查客户和婚宴；新建/修改/跟进分别确认卡片，获批后读回。签单后
生成并送达 Word，选择已送达版本和指定同事提交交接；接手人通过婚宴记录
编号打开 `handoff`，实际读材料后确认或说明缺项退回。改材料后重新提交新版。
原生提醒验收未通过前，不承诺通知送达，也不另建重复个人提醒。

提醒：视图筛选不构成权限隔离；新资源必须纳入实际共享范围核验。
本地查询暂以 2000 条为上限，超出明确拒绝，不宣称适合规模化正式数据。
